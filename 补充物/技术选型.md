## 2. 逐维度对比

> 评分口径：★ 越多越好；「医疗适配度」= 该候选在医疗信息系统场景（密集表格、表单、权限、多机构）的贴合程度。

### 2.1 框架：Vue3 vs React

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **Vue3**（Composition API + `<script setup>`） | ① 国产 HIS/EMR **事实标准**（OpenHIS/云HIS 均用）② Element Plus / VxeTable 生态原生配套 ③ 模板语法上手快，团队/教学友好 ④ 中文文档与社区最厚 | ① 大型工程化（微前端、复杂状态）生态不如 React 广 ② 高级 TS 类型推导弱于 React | ★★★★★ | **首选【待确认】** |
| **React 18/19** | ① 国际医疗（Bahmni 用 React）与大型前端生态最广 ② TS 类型与组合能力强 ③ 人才池大 | ① 国产 HIS 落地案例少，**行业范式契合度低** ② UI 中后台套件需另选（Ant Design）③ 教学成本高于 Vue | ★★★☆☆ | 备选【待确认】 |

> **倾向**：**Vue3**。理由：本项目要"贴合国内 HIS 行业范式"且是校企教学项目，Vue3 与主流 HIS 一致、学习曲线平缓、配套 UI 库现成。**最终以评审确认为准。**

### 2.2 构建工具：Vite（vs Webpack / Rspack）

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **Vite 6/7** | ① 冷启动/热更极快 ② Vue3 官方推荐，脚手架开箱即用 ③ OpenHIS 已用 Vite7 ④ Node 24 兼容良好 | ① 超大项目生产构建依赖 Rollup，需配置 ② 生态插件质量参差 | ★★★★★ | **首选【待确认】** |
| **Rspack** | ① Rust 实现，构建速度接近 Vite ② Webpack 配置兼容，易迁移 | ① 生态较新，医疗类项目案例少 ② 调试经验不足 | ★★★☆☆ | 备选【待确认】 |
| **Webpack 5** | ① 生态最成熟、可控性最强 ② 老项目事实标准 | ① 启动/热更慢 ② 配置复杂，对教学不友好 | ★★☆☆☆ | 不推荐（除非需历史兼容） |

> **倾向**：**Vite**。与 Vue3 官方脚手架一致，Node 24 无兼容问题。**【待确认】**

### 2.3 UI 组件库：Element Plus vs Ant Design Vue vs VxeTable

> 三者**非完全互斥**：Element Plus / Ant Design Vue 是"通用中后台组件库"，VxeTable 是"专业表格组件库"，可叠加使用（OpenHIS 即 Element Plus + VxeTable 组合）。

| 候选 | 定位 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|---|
| **Element Plus** | 通用组件库（Vue3） | ① 国产 HIS **事实标准**（OpenHIS/云HIS 均用）② 表单/弹窗/日期选择器齐全 ③ 中文文档完善 ④ 主题色易定制（医疗蓝） | ① 原生表格能力中等，超宽密集表需增强 ② 复杂表格性能一般 | ★★★★★ | **首选【待确认】** |
| **Ant Design Vue** | 通用组件库（Vue3） | ① 组件质量高、设计规范严谨 ② 表格/表单能力强于 EP | ① 国产 HIS 落地案例少于 EP ② 与 OpenHIS 范式不完全一致 ③ 包体积偏大 | ★★★★☆ | 备选【待确认】 |
| **VxeTable** | 专业表格（可配任意 UI 库） | ① **虚拟滚动**，支撑 20+ 列密集表（README 第 3.5 节明确要求）② 行内编辑、行内下拉、行内状态标签齐全 ③ OpenHIS 实证 | ① 需与主 UI 库搭配，学习成本叠加 ② 独立文档、风格需与 EP 对齐 | ★★★★★（表格专项） | **建议叠加**（不作主库）【待确认】 |

> **倾向**：**Element Plus 作主库 + VxeTable 补密集表格**。会诊工单/审计日志等页面需要"20+ 列 + 行内状态标签"，VxeTable 的虚拟滚动能兜住性能；其余表单/弹窗用 Element Plus，贴合行业范式。**【待确认】**
> *注：VxeTable 有社区版（免费）与专业版（付费），需确认采用社区版能力是否够用。*

### 2.4 状态管理：Pinia（vs Vuex）

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **Pinia** | ① Vue3 官方推荐，替代 Vuex ② TS 类型友好、无 mutations 样板 ③ OpenHIS 使用 ④ 支持组合式写法 | ① 极大型多模块项目需自行规范分模块 | ★★★★★ | **首选【待确认】** |
| **Vuex 4** | ① 存量项目多 ② 概念成熟 | ① 官方已不推荐新项目 ② 样板代码多、TS 体验差 | ★★☆☆☆ | 不推荐 |

> **倾向**：**Pinia**。Vue3 标配。**【待确认】**

### 2.5 路由：Vue Router 4（vs 其他）

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **Vue Router 4** | ① Vue3 官方路由 ② 支持动态路由/权限守卫（**医疗系统多角色/多机构权限必需**）③ 标签页 keep-alive 成熟方案 | ① 复杂权限路由需自行设计 meta 结构 | ★★★★★ | **首选【待确认】** |
| TanStack Router | ① 类型安全强 | ① 主要面向 React，Vue 支持不成熟 | ★☆☆☆☆ | 不适用 |

> **倾向**：**Vue Router 4**，配合 `meta.roles / meta.permission` 实现多角色菜单与路由守卫。**【待确认】**

### 2.6 请求库：Axios（vs Fetch 封装 / ofetch）

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **Axios** | ① 拦截器（**统一注入 token、留痕请求头、错误码**）成熟 ② 国产 HIS 事实标准 ③ 取消请求、超时、上传进度完备 | ① 需额外封装统一响应体/错误处理 | ★★★★★ | **首选【待确认】** |
| 原生 Fetch 封装 | ① 无依赖、体积小 ② 原生支持 | ① 拦截器/超时/进度需自行实现 ② 样板多 | ★★★☆☆ | 备选【待确认】 |
| ofetch | ① 轻量、API 友好 | ① 生态与拦截器方案不如 Axios 成熟 | ★★☆☆☆ | 备选 |

> **倾向**：**Axios**，统一封装 `request` 实例：请求拦截注入 token/机构/留痕头，响应拦截统一处理业务码与 401。**【待确认】**

### 2.7 图表库：ECharts（vs 其他）

| 候选 | 优势 | 劣势 | 医疗行业适配度 | 推荐倾向 |
|---|---|---|---|---|
| **ECharts 5** | ① 国产、中文文档好 ② 图表类型全（折线/饼/雷达，OpenHIS 统计卡实证）③ 与 Vue3 集成简单（vue-echarts）④ 大数据量可配 | ① 包体积需按需引入 ② API 偏重 | ★★★★★ | **首选【待确认】** |
| AntV G2/G6 | ① 图形语法灵活 ② G6 适合关系图 | ① 上手成本高 ② 与 EP 生态不搭 | ★★★☆☆ | 备选（如需关系图） |
| Chart.js | ① 轻量 | ① 图表类型少、复杂医疗统计不够用 | ★★☆☆☆ | 不推荐 |

> **倾向**：**ECharts**，按需引入 + `vue-echarts`。工作台指标卡、统计报表用。**【待确认】**

## 3. 推荐技术栈组合方案（1–2 套）

### 方案 A · 国产 HIS 主流范式（**推荐首选**）

```
Vue3 + TypeScript + Vite
  + Element Plus（主 UI）+ VxeTable（密集表格）
  + Pinia（状态）
  + Vue Router 4（路由/权限）
  + Axios（请求）
  + ECharts（图表）
```

- **推荐理由**：与 OpenHIS / 云HIS **完全同构**，最大化"贴合行业范式"；教学项目上手快；Node 24 全兼容；中文生态与文档最厚。
- **取舍**：① VxeTable 增加一层学习/依赖成本（社区版能力需确认）；② 若团队无 Vue 基础，需少量预热。
- **适用**：本项目默认推荐。

### 方案 B · 单库轻量（备选，若不想引入 VxeTable）

```
Vue3 + TypeScript + Vite
  + Element Plus（唯一 UI 库）
  + Pinia + Vue Router 4 + Axios + ECharts
```

- **推荐理由**：依赖最少、约定最简，适合"先跑通再增强"。
- **取舍**：超宽密集表（20+ 列）性能与行内编辑能力弱于方案 A，后续可能仍需补表格增强。
- **适用**：若评审认为 VxeTable 过重，或团队以教学演示为主。

### 对照方案 C · React 系（仅作对照，**不推荐**）

```
React 18 + TypeScript + Vite + Ant Design + Zustand/Redux + React Router + Axios + ECharts
```
- 说明：技术本身优秀，但**与国产 HIS 范式偏离**，本项目不推荐，仅列出供评审对比。

> **拍板建议**：默认采用 **方案 A**，方案 B 作为降级选项。**最终结论待评审确认。**

## 5. 目录结构约定

> 对齐 README 第 2 节（OpenHIS `apps/web-ele/src/` 结构）与第 3 节（页面骨架四层）。若采用方案 A 的 Vben Admin Monorepo，则为 `apps/web-ele/src/`；若采用方案 B 单应用，则为 `src/`。**以下以单应用 `src/` 表述，Monorepo 下同构。**

```
src/
├── api/            接口层（按业务域分文件）
│   ├── consult.ts     会诊工单
│   ├── record.ts      会诊记录
│   ├── audit.ts       合规审计
│   └── auth.ts        登录/机构
├── views/          页面（与路由一一对应）
│   ├── login/         登录
│   ├── dashboard/     工作台/首页
│   ├── consult/       会诊工单（列表/发起/协同工作台）
│   ├── record/        会诊记录（列表/详情签署）
│   └── audit/         合规与审计
├── components/     公共组件（跨页面复用）
│   ├── StatusTag/     状态标签（色点+文字，见第 8 节状态字典）
│   ├── AmountText/    金额文本（右对齐两位小数）
│   ├── DateTimeText/  时间文本（yyyy-MM-dd HH:mm:ss）
│   ├── ProTable/      列表页三件套封装（搜索+表格+分页）
│   └── PageCard/      详情页卡片（标题+右上编辑+空态）
├── router/         路由与权限守卫
│   ├── index.ts       路由实例
│   ├── routes.ts      路由表（含 meta.roles/permission）
│   └── guard.ts       全局守卫（登录态、权限、留痕）
├── store/          业务 Store（Pinia）
│   ├── user.ts        用户/机构/角色
│   ├── consult.ts     会诊工单状态
│   └── app.ts         全局 UI 状态（侧栏折叠等）
├── layouts/        布局（对齐 README 第 3.1 节四层骨架）
│   ├── DefaultLayout/ 顶部栏 + 左导航 + 主区 + 底部状态栏
│   └── BlankLayout/   登录页等无壳布局
├── utils/          工具（request 封装、时间/金额格式化、字典）
├── styles/         全局样式与主题变量（医疗蓝、状态色）
├── assets/         静态资源
└── types/          TS 类型定义
```

**约定要点**
- `api/` 按**业务域**分文件，不按 HTTP 方法分。
- `views/` 目录名 = 业务域，与路由 path 对应；页面文件用 `index.vue` 或语义名（如 `ConsultWorkbench.vue`）。
- `components/` 只放**跨页面复用**组件；页面内私有子组件放该页目录下 `components/`。
- `layouts/` 严格实现 README 第 3.1 节的**四层骨架**：①顶部栏 ②左侧导航 ③主内容区 ④底部状态栏。

## 6. 组件命名规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 组件文件 | **大驼峰 PascalCase**，多词 | `ConsultWorkbench.vue`、`StatusTag.vue` |
| 目录（组件） | PascalCase（与组件同名，含 `index.vue`） | `components/ProTable/index.vue` |
| 页面组件 | PascalCase 语义名 | `views/consult/ConsultList.vue` |
| 路由 `name` | 大驼峰，唯一 | `name: 'ConsultWorkbench'` |
| Props / 事件 | props 用 camelCase；事件用 `kebab-case`（模板）/ camelCase（defineEmits） | `:patient-name`、`@row-click` |
| 组合式函数 | `use` 前缀 camelCase | `useConsultStore`、`usePermission` |
| Store | `use{Xxx}Store` | `useUserStore` |
| 常量/字典 | 全大写下划线 | `CONSULT_STATUS`、`STATUS_COLOR` |
| 类型/接口 | PascalCase，前缀区分 | `IConsultOrder`、`ConsultStatus` |

## 7. 编码约定

### 7.1 通用

- **语言**：TypeScript（严格模式 `strict: true`），禁用 `any`（必要时 `unknown` + 断言）。
- **缩进**：2 空格；**分号**：保留；**引号**：单引号（Prettier 统一）。
- **代码检查**：ESLint + Prettier + `@vue/eslint-config-typescript`，提交前 `lint-staged` 校验。
- **命名**：变量/函数 camelCase；常量 UPPER_SNAKE；布尔值用 `is/has/can` 前缀。
- **注释**：仅在逻辑不直观处写；接口函数标注入参/返回类型。

### 7.2 时间格式（铁律，README 第 3.5 / 5.4 节）

- **展示统一 `yyyy-MM-dd HH:mm:ss`**（如 `2026-10-16 09:12:00`）。
- 日期范围搜索用 `yyyy-MM-dd`；仅日期不显示时间。
- 通过统一工具 `formatDateTime()` 输出，**禁止各页面自行拼接**。
- 存储/传输建议 ISO 8601（`YYYY-MM-DDTHH:mm:ssZ`），展示层转换。

### 7.3 金额格式（铁律，README 第 3.5 / 5.4 节）

- **右对齐 · 两位小数 · 千分位**（如 `1,175.00`）。
- 负数带符号右对齐（如 `-175.00`）。
- 只读/不可编辑金额**置灰**。
- 通过统一组件 `AmountText` / 工具 `formatAmount()` 输出，**禁止手写 `toFixed`**。

### 7.4 状态色字典（对齐 README 第 5.3 节会诊状态机）

> 用 `StatusTag` 组件渲染「色点 + 文字」。色值对齐 README 第 5.4 节。

| 已受理 | 已确认参与方 | 🔵 蓝 | `#1677ff` | 红线2 资质核验 |
| 排期/待开始 | 已约定时间 | 🟡 黄 | `#faad14` | 红线3 首诊红线（校验） |

| 已作废 | 异常终止 | 🔴 红 | `#f5222d` | 红线9 全程留痕 |

**通用状态色约定**：绿=正常/进行中 · 黄=待办 · 红=异常/停止 · 蓝=信息 · 橙=待签署 · 灰=待受理。
