## 一、选型对比

> 评分口径：医疗行业适配度 = 该候选在**本项目**具体场景下的贴合程度（密集表格、多机构、四层骨架、留痕/脱敏/签名、音视频+影像工作台），不泛论行业。
> 适配度用 5 分制文字描述，不用星级——星级容易被当成"技术优劣"，而这里衡量的是**贴合度**。
>
> **状态说明（本版起）**：8 个维度**全部已定**——"状态"列统一为已定，"推荐倾向"标为 **定稿** 的即最终选型。**未采用的候选一律保留**，因为评审一定会问"为什么不用另一个"，答案在"劣势"列里；**回退条件**统一写在第二节 S-xx，本节不重复。
>
> **本节只覆盖前端。** 后端选型（框架 / 数据库 / 持久层）见 **3.8.1～3.8.3**，对比口径相同（贴合度而非技术优劣）。

## 三、不依赖选型的架构约束

> 本节是全文价值最高的部分：**换框架不改本节**。定下来即可拆 WBS。

### 3.1 目录结构约定

**分层原则**：顶层按"层"分（可复用性递减、业务性递增），二级按"业务域"分。**禁止**按页面分、按人分、按文件类型平铺。

> **仓库布局（本版新增，与 A-01 的调和见第二节）**：`src/` 仍是**前端应用**的根——A-02 不变，所有既有路径引用继续有效。仓库根新增两个目录：`server/`（后端，见 3.8.3）与 `shared/`（契约包，见 S-10）。三者的依赖方向：`src/` 与 `server/` 都依赖 `shared/`，**二者之间零依赖**（只通过 HTTP 契约通信）。

**新增一个业务模块，文件放哪（SOP，以"随访管理"为例）**

1. **路由**：新建 `router/routes/followup.ts`，`meta` 写 `{ title:'随访管理', permission:'followup:plan:list', keepAlive:true }`，在 `routes/index.ts` 注册。

3. **留痕动作**：在 `domain/audit/actions.ts` 声明本模块需留痕的动作（如 `FOLLOWUP_PLAN_EXPORT`），未声明则不允许调用留痕接口。
4. **接口**：新建 `api/followup.ts` + `types/followup.ts`，响应体必须过 `ApiResponse`。
5. **状态**：若跨页面共享才建 `store/modules/followup.ts`；仅本页用的状态留在组件内。
6. **页面**：`views/followup/FollowupList.vue`、`FollowupDetail.vue`，私有子组件放 `views/followup/components/`。
7. **字典**：若有新状态，先在 `domain/consult` 同级的字典里登记，再补 3.3 状态字典——**禁止在页面里硬编码状态中文或色值**。

**命名约定**

| 对象 | 规范 | 示例 |
|---|---|---|
| 页面/组件文件 | PascalCase，多词 | `ConsultWorkbench.vue`、`StatusTag.vue` |
| `views/` 目录 | 小写单词，等于路由一级 path | `consult`、`record` |
| `api/` 文件 | camelCase 单数，等于业务域 | `consult.ts` |
| 路由 `name` | PascalCase，全局唯一 | `ConsultWorkbench` |
| 路由 `path` | kebab-case，层级用 `/` | `/consult/workbench/:id` |
| 权限点 | `域:资源:动作`，全小写 | `consult:order:create` |
| 留痕动作 | UPPER_SNAKE | `EMR_RECORD_READ` |
| 字典/常量 | UPPER_SNAKE | `CONSULT_STATUS`、`STATUS_TOKEN` |
| 类型 | PascalCase，实体无前缀 | `ConsultOrder`、`PageResult<T>` |

### 3.2 模块边界

**四个业务域**（【实证】用户故事集四大模块，与 F1–F5 功能清单对齐）

| 域 | 代号 | 职责 | 对应功能 | 对应故事 |
|---|---|---|---|---|
| 音视频会诊 | `AV` | 房间、邀约、音视频、录制 | F2 | US-AV-01～07 |
| 病历共享 | `EMR` | 授权调阅、时间轴、共享快照、脱敏 | F3 | US-EMR-01～05 |
| 会诊记录 | `REC` | 结构化记录、分区署名、签署、归档 | F1（状态机）、F4 | US-REC-01～06 |
| 多方协同 | `COL` | 会场角色与发言权、协同标注、状态监控、时序事件 | F1、F5 的展示面 | US-COL-01～04 |

**共享内核（Kernel）**——先于业务域落地，否则四个域各写一套：

| 内核能力 | 内容 | 依据 |
|---|---|---|
| **患者上下文** `patientContext` | 当前患者（脱敏视图）、授权范围、会话票据；工作台与记录页共用 | R8 最小必要 |
| **权限** `authz` | 权限点常量、角色映射、路由守卫、按钮级判断 | A-10 |
| **留痕** `audit` | 动作枚举、上报器、traceId 生成与透传 | R9 |
| **字典与格式化** `dict` | 状态/类型/科室字典、时间/金额/脱敏格式化 | A-05 |
| **请求层** `api/request` | 拦截器三件套 | A-07/A-09/A-11 |
| **布局壳** `layouts` | 四层骨架、机构切换、底部状态栏 | README 3.1 |

**依赖方向（单向，禁止反向与横向直连）**

```
        views/*  （页面层，可依赖 domain / store / components）
           │
           ▼
   domain/*  （业务规则：状态机、权限点、留痕动作、脱敏规则）
           │
           ▼
  kernel  （patientContext / authz / audit / dict / request / layouts）
           ▲
           │  只允许通过 kernel 暴露的接口访问
   api/*  ──┘  （协议层，被 domain 与 views 调用，不反向依赖）

域间横向依赖：只允许 3 条，其余一律禁止
  REC ──读取──▶ EMR   的"共享快照"（US-EMR-02：共享清单生成快照，随记录归档）
  AV  ──发布──▶ COL   的时序事件总线（US-REC-06：语音/标注/意见统一时间戳）
  REC ──发布──▶ COL   的时序事件总线
  ✗ EMR 不得依赖 REC（病历域不知道记录域存在）
  ✗ AV 不得依赖 REC
```

> **为什么只放这 3 条**：三条都能在【实证】里找到原文依据（US-EMR-02 的快照归档、US-REC-06 的统一时间戳），其余耦合都是"图省事"。域间一旦横向直连，story 就无法按域并行，WBS 会退化成串行。

**F1 状态机的归属**：会诊工单状态机（待受理→已受理→排期→进行中→待签署→已归档/已作废，【实证】README 5.3）属于 **REC 域**，但被 AV/EMR/COL 读取。落地方式：`domain/consult/stateMachine.ts` 单点定义"当前态 + 动作 → 目标态 + 所需权限 + 所需留痕"，任何域要改状态只能调它，不许自己 set。

**E. 五条使用规则**

1. **色不单独承载语义**：状态标签必须是"色点 + 文字"，色盲用户可读（无障碍）。
2. **状态与标记分离**：主态只能有一个；flag 可多个叠加。禁止出现"进行中-超时"这种复合枚举。
3. **大面积不用状态色**：状态色只用于色点、标签、角标、行左色条；禁止整行/整卡铺色。
4. **新增颜色先改字典**：任何页面需要新语义色，先在本表登记 token，再改代码。
5. **语义优先级**：`红=异常/终止` > `橙=待签署` > `黄=待办` > `绿=正常` > `蓝=信息` > `灰=待处理/已失效`。

> 待确认项：【推断】"已取消（用户主动撤销）"与"已作废（异常终止）"是否是两个状态——README 5.3 只有一个终态"已作废"（红）。当前按**同一状态**处理；若业务要区分，则拆为"已取消=灰"与"已作废=红"，需产品确认。

### 3.4 格式化规范

**A. 时间**

| 场景 | 格式 | 示例 | 规则 |
|---|---|---|---|
| 列表/详情/记录正文 | `yyyy-MM-dd HH:mm:ss` | `2026-10-23 09:12:00` | 【实证】README 3.5/5.4 铁律 |
| 日期范围搜索 | `yyyy-MM-dd` | `2026-10-01 ~ 2026-10-23` | 仅日期不显示时间 |
| 传输（接口） | ISO 8601 带时区 | `2026-10-23T09:12:00+08:00` | 【推断】展示层统一转本地时区 |
| 存证时间轴（同日） | `HH:mm:ss` | `09:15:03` | 跨日必须显示完整日期，禁止只显示时分 |
| 时长 | `hh:mm:ss` / `mm:ss` | `00:42:17` | 会诊时长、录制时长 |
| 相对时间 | **禁止** | ✗ "3 分钟前" | 【推断】病历/留痕/签署场景要求可举证，必须是绝对时间；唯一例外是站内消息列表 |

统一入口：`formatDateTime()` / `formatDate()` / `formatDuration()`。**禁止页面自行拼接日期字符串**（不允许出现 `getFullYear() + '-'`）。

**B. 金额**

| 规则 | 说明 |
|---|---|
| 对齐 | 表头与单元格**右对齐**（【实证】README 3.5 OpenEMR 就诊历史） |
| 精度 | 固定两位小数 + 千分位：`1,175.00` |
| 负数 | 带负号且保持右对齐：`-175.00` |
| 币种 | 表头统一标注（`金额(元)`），单元格不重复符号 |
| 只读 | 置灰显示，不显示输入框边框 |
| 空值 | 显示 `—`，仍保持右对齐 |
| 计算 | 【推断】禁止 JS 浮点直接累加；以"分"为整数或 decimal 字符串传输，展示层再格式化 |

统一入口：`formatAmount()` / `<AmountText>`。**禁止手写 `toFixed`。**

**C. 脱敏展示**

| 字段 | 默认展示 | 二次授权后 | 说明 |
|---|---|---|---|
| 姓名 | `李*`（保留首字，其余替换为 `*`） | 全名 | 【实证】README 4.2 ② 列表"李*" |
| 身份证号 | `110***********1234`（前 3 后 4） | 全号 | 【推断】 |
| 手机号 | `138****8000` | 全号 | 【推断】 |
| 住院号/病历号 | `****1234`（后 4 位） | 全号 | 【推断】**搜索框仍输入完整值**（后端匹配），解决"可检索但不可见"的冲突 |
| 诊断/检验值 | 不脱敏 | — | 【推断】诊疗必需，列表页只展示摘要 |
| 影像 | 患者信息区脱敏 + 水印 | — | 【推断】影像本体是诊疗必需内容，靠水印与留痕管控 |

规则：① 脱敏由**后端返回**（A-06），前端只渲染；② 二次授权走"申请 → 审批 → 重新请求"链路，**前端不做本地解掩码**；③ 明文禁止进入 `localStorage`、埋点、控制台日志、错误上报。

**D. 空值与加载态（三者不混用）**

| 场景 | 展示 | 说明 |
|---|---|---|
| 只读展示、无数据 | `—`（em dash） | 不用空白、不用 `null`/`N/A`/`-`（半角连字符） |
| 表单编辑、未填写 | 留空 + placeholder | 不预填 `—`，避免被当成值提交 |
| 加载中 | 骨架屏 | 不用空白表格，避免"看起来没数据" |
| 加载失败 | `加载失败，点击重试` | 灰底提示条（【实证】README 3.5 空态范式） |
| 无权限 | `无权限查看` + 申请入口 | 与"无数据"必须区分，否则用户会以为数据丢了 |
| 必填未填（校验态） | `未填写` + 红色边框 | 仅表单校验时出现，只读态永不出现 |

**A. 已定接口清单（原样承接，不得改名）**——【实证】板块三第 4 步

**B. 统一响应体**

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "3f9c1a2b7e4d",
  "timestamp": "2026-10-23T09:12:00+08:00"
}
```

- `code = 0` 为成功，非 0 一律走错误分支。
- **HTTP 状态码只管传输与会话层**（`401` 未登录、`403` 无权限、`429` 限流、`5xx` 系统错误）；**业务规则失败统一 `HTTP 422` + `code` 细分**。理由：避免"业务失败也返回 200"和"用 HTTP 码承载业务语义"两种混乱。
- `traceId` 由前端生成并在请求头透传，后端回填；留痕与问题排查共用同一 ID。

**C. 分页**

| 方向 | 字段 | 约定 |
|---|---|---|
| 请求 | `page` / `pageSize` / `sortBy` / `sortOrder` | `page` 从 1 起；`pageSize` 默认 20、上限 100 |
| 请求 | 业务筛选参数 | **平铺在 query 上**（`patientName`、`status`、`dateFrom`、`dateTo`），不包一层 `filter` |
| 响应 | `data: { list, total, page, pageSize }` | `list` 为当前页数组；`total` 为总条数 |

**D. 错误码分段**

| 段 | 域 | 示例 | 前端行为 |
|---|---|---|---|
| `0` | 成功 | — | 正常渲染 |
| `1xxxx` | 通用/会话 | `10001` 参数校验失败、`10002` 未登录、`10003` 无权限、`10004` 资源不存在、`10005` 幂等冲突、`10006` 限流 | 统一提示；`10002` 跳登录；`10003` 显示无权限页 |
| `2xxxx` | 会诊工单 | `20001` 机构协议未签署（R1）、`20002` 资质无效/过期（R2）、`20003` 首诊拦截（R3）、`20004` 超执业范围（R16）、`20005` 状态机非法流转 | **拦截类必须给出"原因 + 下一步"**（如 `20003` → 提示转线下首诊，并给出建首诊记录入口） |
| `3xxxx` | 病历/授权 | `30001` 未授权、`30002` 授权过期、`30003` 越界调阅 | `30002` 触发重新申请授权；`30003` 告警并留痕 |
| `4xxxx` | 记录/签署 | `40001` 关键字段缺失、`40002` 未签署禁止归档（R6）、`40003` 签名校验失败 | `40002` 高亮未签方 |
| `5xxxx` | 音视频/协同 | `50001` 房间创建失败、`50002` 参会方超限、`50003` 录制启动失败 | 降级提示 + 重试入口 |
| `6xxxx` | 合规/审计 | `60001` 留痕写入失败 | **fail-closed：阻断当前操作**并提示"系统繁忙，操作未执行"（A-11） |
| `9xxxx` | 系统 | `90001` 内部错误 | 通用错误页 + 展示 traceId 供报障 |

**E. 鉴权与上下文头**

| 头 | 必填 | 说明 |
|---|---|---|
| `Authorization: Bearer <token>` | 是 | 除登录接口外全量注入 |
| `X-Org-Id` | 是 | 当前机构；R1 要求请求可归属到机构 |
| `X-Trace-Id` | 是 | 前端生成，贯穿留痕与排障；后端校验格式，缺失/非法时补生成并回填（见 3.8.4 A5） |
| `X-Authz-Ticket` | 敏感接口 | 会话级授权票据，由 `POST /authz/tickets` 审批后签发（不随调阅接口发放），**离开会场即失效**（R8）；签发/校验/回收见 3.8.4 B2 |
| `Idempotency-Key` | 写操作 | `POST /consultations`、`POST .../sign` 必带，防重复提交（签署尤其不能重放） |

**C. 前端三级组织**

| 级别 | 落地 | 机制 |
|---|---|---|
| **路由级** | 菜单是否出现、直接输 URL 能否进入 | 路由 `meta.permission` + 全局守卫；菜单由权限点集合生成（`router/menu.ts`），不手写死菜单 |

**D. 命名与同步**：权限点 `域:资源:动作`，唯一来源 `domain/authz/permissions.ts`，与后端权限表**同名同义**。新增权限点必须两侧同时提交，否则视为未完成。

**E. 一条底线**：前端权限只解决"体验与误操作"，**任何越权拦截都必须由后端返回 `10003`/`3xxxx` 兜底**。验收时须包含"用低权限 token 直调接口"的负向用例。

### 3.7 合规相关的架构级要求

> 这一节不能等写页面时再想——它决定了拦截器、路由守卫、组件库三处的形态。

**A. 全程留痕审计（R9）——三层落点**

| 层 | 做什么 | 不做什么 |
|---|---|---|
| **前端** | 统一请求拦截器自动注入 `traceId`；对"UI 侧动作"（展开明文、导出、打印、离场、录制起止）显式调用上报接口；动作枚举来自 `domain/audit/actions.ts` | **不生成权威日志**。前端日志可被篡改/屏蔽，不能作为审计证据 |
| **后端** | 独立审计服务/独立表，**仅追加（append-only）**，业务代码无 update/delete 权限；写入与业务同事务或"先写日志后执行业务"（三条路径的精确划分见 3.8.4 A3） | 不与业务表混存（否则业务改数据会连带改日志）。**注**：3.8.2 的"同库不同 schema"不违反本条——隔离靠 schema + role + 触发器，不靠物理分库 |
| **展示** | `views/audit/` 只读查询 + 导出；日志详情展示 `traceId` 便于串联 | 不提供编辑/删除入口 |

**必留痕动作清单**：`LOGIN` / `CONSULT_CREATE` / `INVITE` / `ROOM_JOIN` / `ROOM_LEAVE` / `EMR_READ`（含 scope 与字段范围）/ `EMR_EXPORT` / `MASK_REVEAL`（展开明文）/ `OPINION_WRITE` / `SIGN` / `ARCHIVE` / `VOID` / `PERM_CHANGE` / `RECORDING_START` / `RECORDING_STOP` / `RECORDING_VIEW` / `AUDIT_EXPORT`。

**日志字段（最小集）**：`traceId, actorId, actorRole, orgId, action, resourceType, resourceId, patientId(脱敏), scope, result, failReason, ip, userAgent, ts`。留存 **≥ 6 个月**（【实证】R9）。

**失败策略（关键）**：**敏感操作（调阅/导出/签署/归档/展开明文）留痕失败 → 拒绝执行**（`60001` + fail-closed）。宁可业务失败，不可无痕成功——这是 R9 的架构底线。

**B. 敏感字段脱敏（R8）——分层职责**

| 层 | 职责 |
|---|---|
| 传输 | 全站 HTTPS；前端不做额外加密（自研加密无收益，且会被误当安全措施） |
| 后端 | **默认返回脱敏值**；`fields` 参数决定字段范围，`scope` 决定授权范围，`ttl` 决定有效期；二次授权后重新下发明文 |
| 前端 | ① 只渲染，不解掩码；② 明文不落 `localStorage`/`sessionStorage`/埋点/console；③ 页面离开或票据过期即丢弃内存中的明文；④ 打印/导出加水印（操作者 + 时间 + 机构）并留痕 |
| 审计 | `MASK_REVEAL` 必须留痕（谁、何时、展开了哪个字段） |

**架构结论**：脱敏的**安全边界在后端**，前端的责任是"不缓存、不外泄、不落盘、可追溯"。凡是想在前端写 `decrypt()` / `unmask()` 的需求，一律驳回。

**C. 电子签名（R6）——位置与职责**

- **位置**：`REC` 域的**独立签署页/签署动作**，不嵌在记录编辑表单里（避免"边改边签"导致签名与内容不一致）。
- **接口**：`POST /consultations/{id}/sign`（【实证】板块三）。
- **前端只做三件事**：① 展示待签内容**摘要 + 内容哈希**（让签署人确认签的是哪一版）；② 触发签名（PIN / CA / UKey / 人脸，取决于 P-04）；③ 展示签署结果与验签状态。
- **禁止**：前端拼装签名值、前端计算"可信时间"、前端缓存私钥/证书。
- **归档前置**：`POST /consultations/{id}/archive` 由服务端校验"各方签名齐全 + 内容哈希一致"，未签退 `40002`。前端在归档按钮上做前置提示（列出未签方），但**不作为拦截依据**。
- **时序存证（US-REC-06）**：语音转写片段、标注帧、文字意见共用一条时间轴，时间戳由**服务端统一授时**，前端只提交相对序号 + 本地时刻，由服务端归一。

**D. 录制留存（R13）**

- 录制在**媒体服务器侧**执行，前端只发起/停止并留痕；前端不得持有录制文件地址的长期凭证。
- UI 必须**常显录制状态**（工作台顶部红点 + 呼吸动画），满足"录制起止与会诊生命周期一致"。
- 录制调阅走 `RECORDING_VIEW` 留痕 + 授权校验。

**E. 处方解耦（R10）**

- **路由表不提供**"会诊意见 → 开处方"的任何跳转；记录页不 import 处方模块。
- 代码层校验：`views/record/**` 禁止 import `views/prescription/**`（可用 ESLint `no-restricted-imports` 落地）。
- 这是**架构约束，不是产品配置**——不允许做成"开关"。

**F. 等保与境内（R7 / R11）——前端能落的部分**

- 依赖**本地打包**，不从第三方 CDN 加载脚本/字体（供应链 + 境内要求）。
- token 存**内存 + 短期有效 + 刷新机制**，不写 `localStorage`（降低 XSS 后的持久化风险）。
- 不接入任何境外分析/埋点 SDK。
- 其余（加密存储、密评、境内机房）属部署侧，前端不承担，但**上线闸门前端须提供"无第三方外联"的自查清单**。

#### 3.8.1 后端技术栈对比 + 定稿

**五维对比**（维度即评审会问的问题）

| 维度 | **Node + NestJS + TS** | **Java + Spring Boot** | **Python + FastAPI** |
|---|---|---|---|
| **与前端同语言（能否共享类型）** | ✅ 最好。`shared/` 包被两端直接 import，Zod schema 一份两用（S-10） | ❌ 需 OpenAPI 生成，多一层"生成物与实现漂移" | ❌ 同上；且 Python 类型标注与 TS 不同构，生成质量更差 |
| **医疗行业招聘 / 生态** | ⚠️ 弱。国内 HIS 后端以 Java 为主（【实证】技术选型.md 第 1 节：云HIS 后端为 SpringCloud）；NestJS 医疗案例少 | ✅ 最强。HIS、集成平台、HL7/FHIR 组件、工作流引擎都在 Java 侧 | ⚠️ 医疗后端少；但在 AI / ASR / NLP 侧最强 |
| **开发速度（本项目场景）** | ✅ 高。CRUD + 校验 + 拦截器高度模板化，与前端共用一套 lint 与类型体系 | ⚠️ 中。样板多、启动慢；生态给得多，但本项目用不上 | ✅ 高。写起来最快，但异步 + ORM 的事务表达弱于前两者 |
| **课程团队上手成本** | ✅ 低。已学 TS（S-09），只增加"服务端概念"（DI、事务、并发），**不加语言** | ❌ 高。JVM + Maven/Gradle + Spring 全家桶，对 4 人教学团队等于第二门语言 | ⚠️ 中。新语言 + async 范式 + 独立生态 |
| **部署复杂度** | ✅ 单进程 + Docker，镜像小，冷启动秒级 | ⚠️ JVM 内存与镜像体积大，需调参 | ✅ 单进程；但若自建 ASR 需额外 worker/GPU，运维面变大 |
| **合规机制落点**（A-06/A-09/A-11/A-12） | ✅ Guard（鉴权/票据）· Interceptor（响应体/脱敏/traceId）· Pipe（校验），与四条约束几乎一一对应 | ✅ 同等（Filter / AOP / ArgumentResolver） | ⚠️ 需自建中间件约定，无现成范式 |
| **结论** | **定稿（B-01）** | 备选：仅当必须对接 Java 生态 | 备选：仅当自建 ASR/NLP 成为主线 |

**为什么推翻"Spring Boot 更主流"的直觉**（评审最可能挑战这一点，先把话说完）

| 常见论据 | 在本项目是否成立 | 理由 |
|---|---|---|
| "医院后端都是 Java，选 Java 更贴合行业" | ❌ 不成立 | 生态优势的兑现条件是**对接存量系统**。本项目从 0 起，没有 HIS / 集成平台要接。"贴合行业"在本项目里指的是**界面范式**（已由 S-01 兑现），不是后端技术栈 |
| "Java 招聘面广" | ❌ 不成立 | 这是就业导向的论据，本项目是课程交付。且 NestJS 的分层范式与 Spring 同构，概念可平移 |
| "Python 做 AI 方便（US-REC-06 语音转写）" | ⚠️ 部分成立，但不改变结论 | ASR 是**外部服务调用**，不是主后端职责。真要做，以独立 Python 服务或厂商 ASR API 接入，走 adapter（3.8.5）。**为一个 V3 功能换掉全栈语言，不划算** |
| "同语言只是省事，不算架构收益" | ❌ 不成立 | 22 条 story 全是契约密集型（7 态状态机、6×11 权限矩阵、统一响应体、分段错误码）。同语言让"契约"从文档变成**可编译的代码**，这是 S-10 能成立的前提 |

**取舍（明说代价）**：选 NestJS 放弃了 Java 的行业存量生态与成熟中间件；换回来的是"一门语言 + 一份契约 + 一条 lint 规则管两端"。**这是路径成本判断，不是技术优劣判断**——与 1.1 选 Vue3 是同一个逻辑。

**已知短板（不掩饰）**：NestJS 在分布式事务、BPMN 工作流、HL7 FHIR 上远不如 Spring。本项目三者都不需要（无跨库事务、无流程引擎、无 FHIR 对接）；若将来需要，属范围变更。

> **定稿：NestJS 11 + TypeScript。** 回退条件见 B-01——回退到 Fastify + 手写分层，**不换语言**。

#### 3.8.2 数据库

| 维度 | **PostgreSQL 16** | **MySQL 8** |
|---|---|---|
| **审计表只追加（R9）** | ✅ 三件套齐全：独立 role + `REVOKE UPDATE,DELETE`、`BEFORE UPDATE/DELETE` 触发器、`RLS` 行级安全（可按机构隔离） | ⚠️ 前两件可行，**无 RLS**；机构隔离只能靠应用层过滤，少一道防线 |
| **复杂查询（审计统计 / 状态时长）** | ✅ 窗口函数、CTE、`FILTER`、`LATERAL`、`generate_series` | ⚠️ 窗口函数 / CTE 可用；`FILTER`、`LATERAL` 缺失，统计 SQL 要绕 |
| **JSON 字段存表单快照** | ✅ `JSONB` + GIN 索引 + 操作符索引，可索引嵌套键 | ⚠️ `JSON` + 生成列索引，能力弱一档 |
| **状态机约束（7 态）** | ✅ `ENUM` / `DOMAIN` / `CHECK` / 排他约束 | ⚠️ `ENUM` 改值需 DDL；`CHECK` 可用 |
| **DDL 与迁移** | ✅ DDL 事务化，迁移失败可回滚（审计表这类复杂 DDL 尤其重要） | ⚠️ DDL 隐式提交，迁移半途失败会留残局 |
| **运维熟悉度（国内医院）** | 中（近年上升） | 高（存量最多） |
| **信创兼容（R11）** | ✅ openGauss / 人大金仓 / 瀚高均为 PG 系，替换路径最短【推断】 | 部分国产库兼容 MySQL 协议 |
| **结论** | **定稿（B-02）** | 备选：运维规范强制时 |

**三个具体设计决定（比"选哪个库"更重要）**

1. **审计与业务同库、不同 schema、不同 role。**
   - **同库**：fail-closed 要靠**同一事务**（业务写入 + 审计写入一起提交/回滚），跨库做不到强一致。
   - **不同 schema**（`audit`）：权限可单独授予，`app_rw` 对 `audit.audit_log` 只有 `INSERT` / `SELECT`。
   - **不同 role**：应用账号无法 `UPDATE` / `DELETE` 审计行，**连代码写错也改不了**。
2. **开发/测试也用 PostgreSQL（Docker），不用 SQLite。** 本项目大量依赖分区、`JSONB`、触发器、`RLS`——SQLite 一个都没有，用它只会造出"本地全绿、线上全红"。
3. **按月分区（`ts` RANGE）。** 审计表只增不减：R9 要求在线 ≥ 6 个月，R5 又要求病历保存门诊 ≥ 15 年 / 住院 ≥ 30 年，这张表会很大。分区让"归档旧数据"变成 `DETACH PARTITION`，而不是 `DELETE`（后者直接违反只追加）。

> **定稿：PostgreSQL 16。** 回退条件见 B-02（MySQL 需接受"无 RLS"；信创则迁 openGauss / 金仓）。

每个 module 内部固定四个位置：`*.controller.ts` / `*.service.ts` / `*.repository.ts` / `dto/`（Zod schema 从 `shared/` 引入，**不重复定义**）。

**六条依赖规则（违反即评审不过）**

1. controller 只做 HTTP 映射与校验，**不写业务判断**（与前端 3.1 的"`api/` 不得写业务判断"同构）。
2. service 是**唯一的事务边界**：一个用例一个事务，禁止 controller 开事务。
3. domain 是纯 TS，**不 import Nest / Prisma**——这样状态机与脱敏规则可以脱离数据库单测。
4. repository 只暴露接口，Prisma 实现放 `*.repository.prisma.ts`；**禁止跨模块 import 别人的 repository**。
5. adapters 只被 service 通过 port 接口调用；controller **不得直连 SDK**。
6. 模块间通信只走 service 公开方法或领域事件，**禁止横向读表**（对应前端 3.2 的"域间只允许 3 条依赖"）。

> 前端 3.2 的三条域间依赖（REC→EMR 快照、AV→COL 事件、REC→COL 事件）在后端同样成立，落地为：`record` 通过 `emr` 的 service 取快照；`av` / `record` 向 `col` 发布事件。

#### 3.8.4 合规能力的后端落点

> 本节是全篇最关键的部分：**R6 / R8 / R9 能不能验收，取决于这里每一条是否有可执行的验证手段。**

**A. R9 全程留痕——表结构、写入时机、fail-closed、traceId**

*A1. 表结构（`audit.audit_log`，仅追加）*

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `bigserial` | 物理顺序 = 写入顺序，不暴露给前端 |
| `trace_id` | `varchar(32)` | 与请求头同源，贯穿业务日志、审计、响应体 |
| `ts` | `timestamptz` | **服务端时钟**，不接受客户端时间 |
| `actor_id` / `actor_role` / `org_id` | `varchar` | 谁、以什么身份、代表哪个机构（R1） |
| `action` | `varchar(48)` | 来自 `shared/audit-actions`，与前端枚举**同源** |
| `resource_type` / `resource_id` | `varchar` | 操作对象 |
| `patient_id_masked` | `varchar` | **脱敏后**的患者标识——日志里不存明文，否则审计表本身成了泄露源 |
| `scope` / `fields` | `jsonb` | 授权范围与字段清单（`EMR_READ` / `MASK_REVEAL` 必填） |
| `result` | `varchar(16)` | `SUCCESS` / `DENIED` / `ERROR` |
| `fail_reason` | `varchar(64)` | 失败原因（拦截类必填，对应 `2xxxx`） |
| `ip` / `user_agent` | `inet` / `text` | 来源 |
| `prev_hash` / `row_hash` | `char(64)` | 链式哈希：`row_hash = sha256(prev_hash ‖ 规范化(本行))` |

> `prev_hash` 链的价值：不需要 WORM 存储，也能**证明"某行之后没有被删改"**——任何一行被改，其后所有 `row_hash` 都对不上。这是教学项目里"防篡改"最诚实的最小实现。**局限**：能发现篡改，不能阻止有 DBA 权限的人重算整条链；真正的 WORM 需专用存储，属部署侧。

*A2. 只追加的三道锁（缺一不可）*

| 层 | 做法 | 挡住什么 |
|---|---|---|
| 数据库权限 | `app_rw` 对 `audit.audit_log` 仅 `INSERT, SELECT`；`TRUNCATE` 一并回收 | 应用代码写错、ORM 误用 |
| 触发器 | `BEFORE UPDATE OR DELETE ... RAISE EXCEPTION 'audit_log is append-only'` | 有连接权限的人手工改 |
| 应用层 | `AuditWriter` 是唯一写入口，**不暴露** update / delete；ESLint 禁止 `auditLog.update/delete` | 新同事"顺手改一下" |

*A3. 写入时机（三条路径必须分开处理）*

| 路径 | 事务策略 | 失败后果 |
|---|---|---|
| **写操作成功**（签署 / 归档 / 创建工单） | 与业务**同一事务**：业务变更 → INSERT 审计 → COMMIT | 审计写失败 → 整体回滚 → 业务未发生（**fail-closed 天然成立**） |
| **读操作成功**（调阅病历 / 展开明文） | 同一事务内**日志先行**：INSERT 审计 → SELECT → COMMIT | 同上；不会出现"读了但没记" |
| **拒绝路径**（越权 / 拦截 / 校验失败） | **独立事务**补写 `result=DENIED` | 写失败只告警不阻断（业务本就没执行），进 outbox 重试 |

> 为什么拒绝路径要独立事务：它必须**在业务事务之外**存活——业务已经回滚了，日志不能跟着消失。**越权尝试恰恰是最需要留痕的**。

*A4. fail-closed 的实现与验证*

- **敏感动作集合**（`EMR_READ` / `EMR_EXPORT` / `MASK_REVEAL` / `SIGN` / `ARCHIVE` / `AUDIT_EXPORT` / `PERM_CHANGE`）强制走 `AuditWriter.writeOrThrow()`。
- 写入失败 → 抛 `AuditWriteError` → 全局异常过滤器映射 `60001`（HTTP 422）→ 前端 K-08 阻断 UI，提示"系统繁忙，操作未执行"。
- **非敏感动作**走 `writeOrQueue()`（outbox 表 + `jobs` 定时重试），不阻断业务。
- **验收方式（可直接执行）**：`REVOKE INSERT ON audit.audit_log FROM app_rw` → 重放调阅 / 签署 / 归档 → 必须返回 `422 + 60001`，且业务表**无任何变更**；随后 `GRANT` 恢复。这一条就是 WBS 8.2 第 5 条的可执行版本。

*A5. traceId 贯穿*

| 环节 | 做法 |
|---|---|
| 入口 | 中间件读 `X-Trace-Id`，校验格式（16–32 hex）；缺失或非法则**后端生成**（不能假设前端一定合法） |
| 传递 | 存 `AsyncLocalStorage`；日志器、Prisma 中间件、`AuditWriter` 自动读取，**业务代码不手工传参**（手工传必漏） |
| 出口 | 响应体 `traceId` 回填 + 响应头回写；错误堆栈只记 traceId，不记明文 |
| 查询 | `GET /audit/logs?traceId=` 可把"一次请求引发的所有副作用"串起来 |

**B. R8 敏感字段脱敏——在哪一层做、票据怎么签发与回收**

*B1. 脱敏的唯一位置：响应序列化层*

| 方案 | 评价 |
|---|---|
| SQL 层（视图 / 列权限） | ❌ 无法按票据**动态展开**；嵌套 / 聚合结果难处理；规则会散在几十条查询里 |
| controller 手写 | ❌ 必漏。新增接口忘调一次，就是一次泄露 |
| **序列化拦截器（定稿）** | ✅ 全局注册，**唯一出口**；规则集中在 `shared/mask-policy`；按 `{role, scope, ticket}` 动态决定掩码级别 |

- 实现：`MaskInterceptor` 在响应序列化前按字段策略表处理；前端 `MaskedText` 只渲染，**不解掩码**（A-06 不变）。
- 明文禁止进入：日志（pino `redact` 配置）、审计表（存 masked）、错误堆栈、APM、`console`。
- 字段策略与前端 `domain/mask/rules.ts` **同源**（放 `shared/`），避免"前端以为脱敏、后端没脱"。

*B2. 二次授权票据（`X-Authz-Ticket`）*

| 环节 | 做法 | 依据 |
|---|---|---|
| **签发** | `POST /authz/tickets`（申请）→ 审批 → 生成 **256bit 随机 opaque token**，库里只存 `sha256(token)`，绑定 `{actor, org, patient, fields[], scope, exp, session_id, granted_by, reason}` | R8 最小必要 + 可追溯 |
| **为什么不用纯 JWT** | JWT 无法**即时吊销**；R8 要求"离场即失效"，黑名单反而比查表更重。opaque + 一次索引查询 = 可即时吊销、可审计 | — |
| **携带** | 前端放 `X-Authz-Ticket`；Guard 校验：hash 存在、未过期、未吊销、`patient` 与路径一致、请求字段 ⊆ 票据 `fields` | A-09 |
| **回收** | ① 主动 `DELETE /authz/tickets/{id}`（离场时前端调用）② `ROOM_LEAVE` 钩子兜底（前端漏调也不留口子）③ 房间结束按 `session_id` 批量吊销 ④ 登出 / 换机构吊销全部 | R8 |
| **TTL** | 默认 30 分钟，且 ≤ 会诊剩余时长；上限 4 小时（可配） | 【推断】 |
| **留痕** | 签发、每次使用（`MASK_REVEAL` 记字段范围）、吊销各一条 | R9 |

> 一句话：**票据是"一次会诊内、对某患者某几个字段"的短期通行证**，不是"永久解密权"。凡是想签发"长期 / 全字段"票据的需求，一律驳回。

**C. R6 电子签名——接口形态、签什么、怎么验、没有 CA 怎么办**

*C1. 接口形态*

```
POST /consultations/{id}/sign
{
  "recordVersionId": "rv_...",
  "contentHash": "sha256:...",        // 签署人在页面上确认的那一版
  "signerRole": "DO" | "EXP",
  "credentialType": "PIN" | "CA" | "MOCK",
  "credentialProof": { ... }
}
→ 200 { signatureId, signedAt, provider, legalEffect, verifyStatus }
```

*C2. 服务端五步（顺序不可换）*

1. 取 `record_version`（**不可变快照**）→ 规范化序列化（键排序、UTF-8、去空白、时间转 UTC）→ SHA-256
2. 比对客户端提交的 `contentHash`；不一致 → `40003`（签的不是当前版本）
3. 校验签署人：是否为应签方、是否已签、资质是否有效（R2）
4. 调 `SignatureProvider.sign({ contentHash, signer, serverTime })`
5. 写签名记录 + 留痕 `SIGN`（**同一事务**）

*C3. 签什么：签摘要，不签正文*

摘要覆盖：记录正文（规范化）+ 参与方与角色 + 版本号 + 会诊单号。理由：定长、可重算、能证明"签名时内容未被改"。**正文任何修订都必须产生新版本 → 新摘要 → 新签名**——旧签名不会"跟着变"，这正是可举证的关键。

*C4. 验签*

- `GET /consultations/{id}/signatures` 返回每个签名的 `verifyStatus`（`VALID` / `CONTENT_CHANGED` / `CERT_EXPIRED` / `REVOKED`）。
- 归档时内部验签：从不可变版本重算 hash → 公钥验签 → 校验证书有效期 / 链 / 吊销（CA 支持时走 OCSP / CRL）。
- 任一不符 → `40002` / `40003`，归档拒绝（A-12 的前置校验；前端只做提示，**不作拦截依据**）。

*C5. 没有真实 CA 时的降级（P-04 未定）*

| 项 | 做法 |
|---|---|
| Provider | `MockSignatureProvider`：服务端生成 ECDSA P-256 密钥对，私钥存本地加密文件（仅开发环境），**签名值真实可验**，证书为自签 |
| 接口与数据模型 | **完全不变**，只在响应加 `provider: "MOCK"` + `legalEffect: false` |
| 前端表现 | 签署页与记录详情常显"演示环境，不具法律效力"（对应 WBS 8.3 的降级验收） |
| **禁止** | 用"前端算个 hash 存库"冒充签名——既不可验签，也不可举证，等于把 R6 做成装饰 |

**D. R11 境内存储——部署约束**

| 项 | 约束 |
|---|---|
| 组件 | DB、对象存储（录制 / 附件 / 影像）、缓存、日志、备份、镜像仓库**全部境内**；不使用境外托管服务与运行时 CDN |
| 供应链 | npm 走内网镜像 / 私有 registry；`package-lock.json` 入库；CI 跑 `npm audit`；**`postinstall` 拉远端脚本需白名单**（NestJS 生态里常见） |
| 传输与存储 | 生产强制 TLS（R7 等保三级）；数据库与对象存储静态加密由部署侧开启 |
| 密钥 | CA 私钥 / 证书、DB 口令、JWT 密钥走环境变量或本地 KMS，**不入库、不入仓** |
| 边界 | 等保三级测评、密评、机房合规**不是代码能完成的**；代码侧只保证"可加密传输、日志留存 ≥ 6 月、访问控制、无境外外联、可审计"，并在上线闸门提交"外联清单自查" |

**E. 红线 → 后端落点 → 验收方式（一页对照）**

| 红线 | 后端落点 | 可执行的验收 |
|---|---|---|
| **R6** | `modules/record` 签署服务 + `SignatureProvider` | 改正文后重放旧签名 → 验签 `40003`；未签齐归档 → `40002` |
| **R8** | `MaskInterceptor` + 票据 Guard | 无票据调阅 → 全字段脱敏；票据过期 → `30002`；吊销后下一次请求立即失效 |
| **R9** | `AuditWriter` + append-only 表 | 收回 INSERT 权限 → 敏感操作 `422/60001` 且业务表无变更；`UPDATE` 审计行被触发器拒绝 |
| **R11** | 部署清单 + 依赖白名单 | 外联清单（域名 / 依赖 / 镜像源）全为境内，可逐条核对 |

#### 3.8.5 外部依赖的降级策略（P-02 / P-03 / P-04）

**模式：port & adapter。业务只认接口，厂商实现可换。**

| 能力 | port（后端，定义在 `shared/ports`） | fake 实现（今天就能写） | 真实实现等什么 | 换实现的影响面 |
|---|---|---|---|---|
| **音视频**（P-02） | `RtcProvider { createRoom, issueToken, closeRoom, startRecording, stopRecording, onEvent }` | `FakeRtcProvider`：内存房间表 + 假 token + 占位录制文件 + 定时器模拟"超时 / 断连 / 忙线" | 厂商、是否支持 ≥5 方、服务端录制、Web SDK 能否被 Vite 预构建 | 只改 `adapters/video/*`；邀约、入会、录制留痕的业务不动 |
| **DICOM**（P-03） | `DicomProvider { listSeries, getMetadata, getFrameUrl, syncViewport }` | `FakeDicomProvider`：3 组脱敏样本序列 + 静态帧 | SDK 是否支持标注层导出、多端同步能否 < 500ms | 只改 `adapters/dicom/*` 与前端 DICOM adapter；标注 / 记录业务不动 |
| **电子签名**（P-04） | `SignatureProvider { sign, verify, getCertInfo }` | `MockSignatureProvider`：ECDSA 自签，**可自验**，`legalEffect=false` | CA 机构、证书形式（PIN/UKey/人脸）、OCSP | 只改 `adapters/sign/*`；`modules/record` 不动 |

**五条规则**

1. **port 放 `shared/ports`**：前端 adapter 与后端 adapter 各自实现同一接口，联调时方法名 / 参数天然一致。
2. **配置驱动注入**：`VIDEO_PROVIDER=fake|vendor` + Nest `useClass` 工厂；**禁止**在业务里写 `if (provider === 'x')`。
3. **fake 必须能模拟失败**：超时、断连、录制失败、验签失败——否则 `5xxxx` / `40003` 的负向用例无法验收，而那些用例正是红线的验收点。
4. **contract test 双跑**：同一套用例对 fake 与 real 各跑一遍（real 只跑 smoke，需凭据）。
5. **SDK 的异步回调先归一为内部事件**（`room.joined` / `recording.started` / `peer.left`），业务只订阅内部事件；否则换 SDK 会改业务逻辑。

**前后端 adapter 的分界**（避免重复抽象）

| 侧 | 负责 | 不负责 |
|---|---|---|
| 前端 adapter | 播放 / 渲染 / 交互、设备选择、画面布局、标注画布 | 房间生命周期、令牌签发、录制 |
| 后端 adapter | 房间创建 / 关闭、RTC token 签发（**厂商 secret 不下发前端**）、录制编排、回调归一、DICOM 代理（避免前端直连影像源） | 渲染与交互 |

> 判据一句话：**port 里出现厂商专有名词（`agoraChannelId`、`dcm4cheeStudyUid`）就说明抽象漏了**——换 SDK 时业务一定会被拖下水。

- **决策 3 条**：B-01 NestJS 11 + TS · B-02 PostgreSQL 16 · B-03 Prisma。

### 5.3 拆 story 的八条规则

1. **一个 story 必须落在一条线的一个域内**（前端 AV/EMR/REC/COL/Kernel，或后端 consult/av/emr/record/col/audit/common）。跨线 story 先拆成两条，用 `shared/` 契约对齐——这是并行开发的前提。
2. **不要按技术层拆 story**（✗ "写 api 层"、"写 store"、"写 repository"）。story 的粒度是"可验收的行为/接口"，技术层是 story 内部的实现步骤。
3. **每条 story 必须标注三个字段**：权限点、留痕动作、状态流转。**后端 story 额外标"是否敏感动作（fail-closed）"**。
4. **验收标准必须保留原文的量化指标**（≥5 方、<10 秒、丢包 20%、<500ms、≥6 月），不得改写成"支持多方会诊"这类不可测表述。
5. **Kernel 先于业务域**：前端五项（患者上下文、权限点表、留痕上报器、请求层拦截器、字典与格式化）+ 后端五项（traceId、审计写入器、脱敏管道、票据、错误码外壳）都必须先于业务 story 完成。
6. **工作台只拆到"壳 + port 接入"**：中栏在 P-02/P-03 未定前，按 `RtcProvider` / `DicomProvider` 接 fake，验收"接得上、可降级、能模拟失败"，**不验收真实能力**。
7. **后端 story 与前端 story 分开拆**，禁止"前端 + 后端"混合 story：两者验收对象不同（界面行为 vs 接口契约 + 负向用例），混在一起既无法并行也无法判定完成。
8. **每条后端 story 必须带一条负向用例**（越权 / 未授权 / 签名不符 / 审计失败之一）。没有负向用例的后端 story，等于没有验证红线。
